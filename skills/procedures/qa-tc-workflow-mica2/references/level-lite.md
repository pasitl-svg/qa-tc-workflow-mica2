# ระดับ Lite (กระชับ)

เน้นกระชับ อ่านเร็ว — รวม step ที่ต่อเนื่องเป็นหน่วยเดียวได้ และ Expected Result ระบุเฉพาะจุดตรวจสำคัญ (ไม่ต้อง map ทุก step) เหมาะกับ requirement ที่ชัดเจนและ tester ที่คุ้นระบบอยู่แล้ว

**สิ่งที่ยังบังคับเท่ากับระดับอื่น:** TC ID format, สูตร Test Title, Precondition ต้องระบุ role+หน้าจอ+ข้อมูล, ภาษาราชการ/action verb ไทย, ห้ามคำกำกวม, Negative+Edge ≥ Happy, coverage/traceability, column ลูกค้า 13 (รวม Test Type Core/Edge) และ column ภายในครบ, Prod safety

## Test Steps

อนุญาตให้**รวบ action ที่ต่อเนื่องและเป็น flow เดียวกัน**เข้าเป็น 1 step เพื่อความกระชับ ตราบใดที่ยังไม่กำกวมและ tester ทำตามได้ เช่น การกรอกฟอร์ม login หลายช่องรวบเป็น "กรอกอีเมล `test+001@example.com` และรหัสผ่าน `Test@1234` ในฟอร์มเข้าสู่ระบบ" ได้ แต่ถ้าเป็น TC ประเภท Negative/Boundary ที่จุดสนใจอยู่ที่ค่าใดค่าหนึ่งโดยเฉพาะ ให้แยก step ค่านั้นออกมาชัดเจนเสมอ (ห้ามรวบจนกลบ input ที่กำลังทดสอบ)

**ตัวอย่าง (happy path login):**
```
1. เข้าสู่หน้า /login แล้วกรอกอีเมล "test+001@example.com" และรหัสผ่าน "Test@1234"
2. คลิกปุ่ม "เข้าสู่ระบบ"
```

## Expected Result

1. **Numbered list** — ระบุเฉพาะ**จุดตรวจสำคัญ (key checkpoints)** ไม่ต้อง map ทุก step; โฟกัสที่ผลลัพธ์ที่ยืนยันว่า TC ผ่าน/ไม่ผ่าน (เช่น ปลายทางสุดท้าย + ข้อความ/สถานะที่สำคัญ)
2. **ระบุสิ่งที่สังเกตเห็นได้จริง** — ข้อความบนจอ, การเปลี่ยนหน้า, ค่าที่แสดง, สถานะปุ่ม, ค่าใน DB, response ของ API
3. **ภาษาไทยเป็นทางการ** — เช่น "ระบบพาไปยังหน้า...", "ระบบแสดงข้อความ..."

Expected สั้นได้ ไม่ต้องบรรยายทุก field ระหว่างทาง — เขียนเฉพาะผลที่พิสูจน์ criteria ของ TC แต่**ห้ามลดจนกำกวม** ต้องยังระบุค่า/ข้อความ/ปลายทางจริงเสมอ

**ตัวอย่าง (คู่กับ steps ด้านบน):**
```
1. ระบบพาไปยังหน้า Dashboard ภายใน 2 วินาที และแสดงชื่อผู้ใช้ "Test User001" ที่มุมขวาบน
```
(happy path เขียน 1 ข้อจับ outcome สุดท้ายพอ ไม่ต้องแยกผลของทุก step ที่กรอกฟอร์ม)

## Lint เพิ่มเติม

- Lite ไม่บังคับ Expected map 1:1 กับ Steps — ตรวจแค่ว่ามีจุดตรวจครบตาม criteria ของ TC
- TC Negative/Boundary ที่รวบ input ที่กำลังทดสอบไว้กับ action อื่นใน step เดียว → flag
