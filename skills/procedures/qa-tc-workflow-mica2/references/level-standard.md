# ระดับ Standard (ค่าเริ่มต้น)

สมดุลระหว่างความกระชับกับความครบถ้วน — เหมาะกับการส่งลูกค้าทั่วไป

## Test Steps

step ที่เป็น setup ต่อเนื่อง (เช่น การกรอกหลายช่องในฟอร์มเดียว) เขียนแยกทีละช่องได้ตามปกติ แต่ไม่ต้องแตกย่อยการกระทำที่เป็นหน่วยเดียวโดยธรรมชาติ (เช่น "เลื่อนหน้าจอลงไปที่ส่วนท้าย" เป็น 1 step พอ)

**ตัวอย่าง (happy path login):**
```
1. เข้าสู่หน้า /login
2. กรอก "test+001@example.com" ในช่อง Email
3. กรอก "Test@1234" ในช่อง Password
4. คลิกปุ่ม "เข้าสู่ระบบ"
```

## Expected Result

1. **Numbered list** — map เข้ากับ step ที่มี observable outcome: ไม่จำเป็นต้องมีทุก step แต่ทุก step ที่ทำให้เกิดผลที่สังเกตได้ต้องมี expected ตรงกัน
2. **ระบุสิ่งที่สังเกตเห็นได้จริงในข้อนั้น** — ข้อความบนจอ, การเปลี่ยนหน้า, ค่าที่แสดง, สถานะปุ่ม, ค่าใน DB, response ของ API
3. **ภาษาไทยเป็นทางการ** — เช่น "ระบบพาไปยังหน้า...", "ระบบแสดงข้อความ...", "ปุ่ม...ถูก disable"

**ตัวอย่าง (map กับ steps ด้านบน):**
```
1. ระบบแสดงหน้า "เข้าสู่ระบบ" พร้อมช่อง Email และ Password
2. ช่อง Email แสดงค่า "test+001@example.com" และไม่มีข้อความแจ้งข้อผิดพลาด
3. ช่อง Password แสดงเป็นสัญลักษณ์จุด (••••••••) และไม่มีข้อความแจ้งข้อผิดพลาด
4. ระบบพาไปยังหน้า Dashboard ภายใน 2 วินาที และแสดงชื่อผู้ใช้ที่มุมขวาบน
```
