# ระดับ Detailed (ละเอียดสูงสุด)

Test Steps เขียน **1 action ต่อ 1 ข้อ** อย่างเคร่งครัด (ไม่รวบ), Expected Result **map 1:1 ทุก step ที่มี observable outcome**, และระบุการตรวจสอบครบทุกชั้นเท่าที่เข้าถึงได้ (UI / DB / API) เหมาะกับงานส่งราชการที่ต้อง audit, ระบบ critical, หรือให้ tester ใหม่ทำตามได้โดยไม่ต้องถาม

**ข้อแลกเปลี่ยน:** จำนวนบรรทัดต่อ TC มากที่สุดในสามระดับ — ใช้เมื่อความครบถ้วน/ตรวจสอบย้อนกลับได้สำคัญกว่าความเร็ว

## Test Steps

เขียน **1 action ต่อ 1 ข้ออย่างเคร่งครัด ห้ามรวบ** — ทุกการกรอก, ทุกการคลิก, ทุกการเลือก, ทุกการนำทาง แยกเป็นข้อของตัวเอง รวมถึง step ยืนยันสถานะระหว่างทาง (เช่น "ตรวจสอบว่า modal ... เปิดขึ้น") ก่อนดำเนินการต่อ เพื่อให้ tester ใหม่ทำตามได้ทีละบรรทัดและ audit ได้ทุกจุด

**ตัวอย่าง (happy path login):**
```
1. เข้าสู่หน้า /login
2. ตรวจสอบว่าฟอร์มเข้าสู่ระบบแสดงช่อง Email, ช่อง Password และปุ่ม "เข้าสู่ระบบ"
3. คลิกที่ช่อง Email
4. กรอก "test+001@example.com" ในช่อง Email
5. คลิกที่ช่อง Password
6. กรอก "Test@1234" ในช่อง Password
7. คลิกปุ่ม "เข้าสู่ระบบ"
```

## Expected Result

1. **Numbered list ที่ map 1:1 กับ Test Steps อย่างเคร่งครัด** — ทุก step ที่มี observable outcome ต้องมี expected เลขตรงกัน (step 5 → expected 5). step ที่ไม่มีผลสังเกตได้ (เช่น "คลิกที่ช่อง Email") ให้เขียน "ช่อง Email อยู่ในสถานะ focus (เคอร์เซอร์กะพริบ)" หรือ "—" หากไม่มีการเปลี่ยนแปลงใดบนจอ — แต่**คงเลขข้อไว้ครบทุก step**
2. **ระบุสิ่งที่สังเกตเห็นได้จริงในข้อนั้น** — ข้อความบนจอ, การเปลี่ยนหน้า, ค่าที่แสดง, สถานะปุ่ม
3. **ครอบคลุมการตรวจสอบครบทุกชั้นเท่าที่เข้าถึงได้** — สำหรับผลลัพธ์ปลายทาง ให้ระบุการตรวจทั้ง **UI** (สิ่งที่ผู้ใช้เห็น), **DB** (ค่าใน table/column เมื่อมี DB access), และ **API** (status + field ใน response เมื่อมี API) แยกเป็นข้อย่อยของ expected นั้น
4. **ห้าม prefix label** เช่น `[UI]`, `[DB]`, `[API]` หรือ `UI:`, `DB:`, `API:` (ระบุเป็นประโยคไทยว่าเห็นอะไรที่ชั้นไหนแทน เช่น "ในตาราง users คอลัมน์ ...") ข้อย่อยตามข้อ 3 ให้ใช้เลข 7.1, 7.2, 7.3
5. **ภาษาไทยเป็นทางการ** — เช่น "ระบบพาไปยังหน้า...", "ระบบแสดงข้อความ...", "ปุ่ม ... ถูกปิดการใช้งาน"

**ตัวอย่าง (map 1:1 กับ 7 steps ด้านบน):**
```
1. ระบบแสดงหน้า "เข้าสู่ระบบ" ที่ URL /login
2. ฟอร์มแสดงช่อง Email, ช่อง Password และปุ่ม "เข้าสู่ระบบ" ครบทั้งสามองค์ประกอบ
3. ช่อง Email อยู่ในสถานะ focus (เคอร์เซอร์กะพริบในช่อง)
4. ช่อง Email แสดงค่า "test+001@example.com" และไม่มีข้อความแจ้งข้อผิดพลาด
5. ช่อง Password อยู่ในสถานะ focus (เคอร์เซอร์กะพริบในช่อง)
6. ช่อง Password แสดงเป็นสัญลักษณ์จุด (••••••••) จำนวน 8 ตัว และไม่มีข้อความแจ้งข้อผิดพลาด
7. ผลการเข้าสู่ระบบ
   7.1 ระบบแสดงข้อความ "เข้าสู่ระบบสำเร็จ" และพาไปยังหน้า Dashboard ภายใน 2 วินาที พร้อมแสดงชื่อผู้ใช้ "Test User001" ที่มุมขวาบน
   7.2 ในตาราง users คอลัมน์ last_login_at มีค่าเท่ากับเวลาปัจจุบัน (คลาดเคลื่อนไม่เกิน 5 วินาที)
   7.3 API POST /auth/login ตอบกลับสถานะ 200 พร้อมค่า accessToken (รูปแบบ JWT) ใน response body
```

## Lint เพิ่มเติม

- **จำนวนข้อใน Expected Result ≠ จำนวน Test Steps → flag (Detailed บังคับ map 1:1 ทุก step)**
- Step ที่มีหลาย action รวมในข้อเดียว (มีคำเชื่อม "แล้ว/และ" คั่นสอง action) → flag (Detailed ห้ามรวบ)
- ผลลัพธ์ปลายทางที่มี DB/API access แต่ Expected ระบุแค่ UI → warning (ควรเพิ่มชั้น DB/API)
